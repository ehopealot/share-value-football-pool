## Goals and boundaries

This plan adds enough operational visibility and controlled recovery for a small production pool without introducing another database, message bus, or monitoring platform. PoolDO remains the sole accounting authority. D1 remains directory, provider, projection, and operational-observation storage. R2 audit exports remain evidence exports, not restorable PoolDO backups.

The implementation must preserve these invariants throughout all stages:

- Integer accounting values remain canonical `TEXT`; a reversal and replacement settlement are atomic, and neither account balances nor season float may become negative.
- A D1 observation, projection, health response, or operator record never authorizes a pool command or changes accounting.
- Public health and email content contain only coarse check kind/status/time. They never contain pool/member identifiers, email addresses, hidden selections, raw provider evidence, secrets, or exception details.
- Operator authority is an immutable server-side user-ID allowlist. Commissioner role and email address are insufficient. Missing/malformed operator configuration fails closed.
- Every sensitive operator or commissioner mutation requires same-origin CSRF validation, a current authenticated session created within the existing 15-minute recent-auth window, a non-empty bounded reason, a stable caller-generated operation ID, and durable audit.
- Unknown or stale observations are not healthy. Only a successful, current healthy observation recovers an incident.
- Time-based notifications use one clock: an obligation must remain continuously unmet (`failed` or observation `unknown`) until 30 minutes after its expected deadline, or for 30 minutes when there is no separate deadline. There is no second grace period.
- Worker rollback never rolls database state back. Every migration is additive, and a rollback target must understand all authoritative rows that can already exist.
- No automatic watchdog repair, direct settlement trigger, exhausted-outbox reset, synthetic result, automatic season reopen, or automatic canary replenishment is introduced.

## Reconciled current state

The approved source anchors match the base, with these implementation details affecting the design:

- `wrangler.jsonc` has one `*/2 * * * *` trigger. `src/index.ts` independently starts odds and backup promises, but stores no overall scheduler heartbeat. `runBackupCron()` logs aggregate failures and `backupPools()` advances a 100-pool cursor; neither records per-pool backup success.
- `src/worker/health.ts` reports coarse state. Several failures still return HTTP 200, `/health/do` proves only that a binding exists, `/health/backups` proves only configuration, and `/health/odds` does not enforce expected cadence.
- `PoolDO.fetch()` commits a business command and then unconditionally sets a near-term alarm. `PoolDO.alarm()` multiplexes `runSettlementAlarm()` and `drainOutbox()`, then unconditionally sets the computed next deadline. Because Cloudflare has one alarm per object and `setAlarm()` replaces it, these are shared-alarm writers that can postpone an earlier deadline.
- `runSettlementAlarm()` already stores event snapshots and supports final/15-minute/24-hour reconciliation. `settleWagers()` currently loops over all active wagers inside one enclosing storage transaction, so one deterministic accounting failure rolls back unrelated wager settlements and lifecycle updates.
- `settlement.ts` correctly rejects `NEGATIVE_ACCOUNT` and `NEGATIVE_FLOAT`, preserves immutable settlement/reversal rows and result identities, handles decisive early multi-leg losses/reopening, and closes eligible seasons only after no unresolved wagers remain. It has no settlement-exception state.
- `outbox.ts` stops automatic delivery at five attempts and retains exhausted rows. There is intentionally no reset path.
- Worker mutations already have same-origin CSRF checks. Selected accounting/admin routes use `sessionIsRecentForUser()` (`15` minutes), and PoolDO rechecks commissioner authority. There is no distinct platform-operator boundary.
- `infrastructureAuditExport()` is not a complete PoolDO image. In particular it omits authoritative members and pool credentials/settings, processed commands, wager quotes, reconciliation/snapshot tables, outbox state, alarms, and some season lifecycle state. It has no importer.
- CI's unit/typecheck job gates deploys. PR browser e2e is broad and nonblocking. Postdeploy validation is an HTTP-200-only `/health/app` probe.

## Cross-cutting data and authorization model

### Operator boundary

Add an `ops` module rather than mixing platform authority into commissioner routes:

- `src/worker/ops-auth.ts`: parse `OPS_OPERATOR_USER_IDS` once per request composition as a strict comma-separated set of non-empty exact user IDs; duplicates, whitespace-only input, or absence make ops unavailable. `requireOperator()` first applies the existing same-origin CSRF rule for mutations, then authenticates with Better Auth, then checks exact user ID, then recent authentication where required.
- `src/worker/ops-routes.ts`: install `/ops/api/*` routes. Read routes require an allowlisted authenticated user; mutations additionally require same-origin CSRF, recent auth, reason, and operation ID. Never accept an actor ID from request JSON.
- `src/web/pages/OpsPage.tsx` and router/navigation seams: render a minimal, unlinked-by-role `/ops` page. Receiving the SPA is not authorization; every data request is protected. Do not expose ops navigation based on commissioner status.
- `OPS_SERVICE_TOKEN`: a distinct Worker/PoolDO secret authenticating only fixed internal inspection/repair paths. Do not reuse settlement, backup, projection, Better Auth, or canary values. The Worker supplies the authenticated operator ID in the internal request; the browser never receives the token.

The allowlist and canary target values are deployment configuration, not D1 rows or UI-editable settings. Configuration readiness is visible to an authorized operator without echoing configured values.

### D1 operational records

Create additive migration `src/db/migrations/0003_operations.sql`. Exact names may change only during implementation review, but the responsibilities must remain separate:

- `ops_sweep_state`: singleton monitoring bootstrap time, lease/run token, lease expiry, bounded pool/backup cursors, cycle start, and last started/progress/completed timestamps. An atomic conditional claim prevents overlapping cron invocations from both advancing a cursor. A lease expiry permits recovery after an abandoned invocation; it is not evidence that the abandoned run succeeded.
- `ops_job_observation`: latest and append-only run observations for `scheduler`, `odds`, `backup`, `watchdog`, and notification delivery. Store status, stable obligation identity, immutable obligation deadline/first-unmet anchor, observed time, safe category, and run token. Retain 30 days with bounded pruning after a successful sweep.
- `ops_pool_observation`: append-only watchdog/backup findings keyed by observation ID plus subject hash/pool ID in access-controlled storage. The ops API maps IDs to safe labels only after authorization. Public responses never include them.
- `ops_incident`: one durable episode at a time per `(check_kind, subject_id)`, with `observing|open|recovered`, underlying status `failed|unknown`, immutable `first_unmet_at` and `notification_eligible_at`, last non-healthy/healthy observations, safe category, and transition sequence. Repeated polls update the episode; category churn does not reset its age. Unknown is an alertable observability condition but never asserts that the underlying business condition failed.
- `ops_notification_delivery`: one immutable row per `(incident_id, transition_sequence, recipient)` with a stable delivery ID, transition kind `opening|recovery`, frozen safe subject/text/HTML payload, prerequisite delivery ID, chain key `(check_kind, subject_id, recipient)`, `pending|claimed|delivered`, cumulative attempt metadata, next attempt, claim token/expiry, and safe error category. Retryable and uncertain sends return to `pending`; there is no terminal lifetime-attempt state. The Resend idempotency key is the stable delivery ID.
- `ops_repair_operation`: immutable operation ID, operator ID, reason, pool ID, request fingerprint, `prepared|succeeded|failed|unknown`, safe before/after scheduling snapshots, and timestamps. Reuse with a different fingerprint is an idempotency conflict.
- Stage 3 adds `ops_canary_run`; it is described there and should be a separate migration so the stage boundaries remain independently releasable.

Operational rows may contain pool IDs and provider/accounting exception categories and are therefore never served by public health endpoints. D1 is sufficient for this small deployment; no additional event pipeline is justified.

### Incident deadlines and notification state machine

Every check emits `healthy`, `failed`, or `unknown` plus a stable obligation identity and deadline. A new non-healthy finding appears in `/ops` immediately. Both `failed` and `unknown` start or continue an alertable episode: `unknown` says observation failed, not that the underlying work failed. The episode freezes `first_unmet_at` at the first continuously unmet obligation and computes one `notification_eligible_at`; retries, category changes, later samples, and mutable `next_attempt_at` values never move either timestamp. Only a successful current healthy observation ends the episode. The implementation publishes and tests these check-specific obligations:

- **Scheduler:** meaningful owned progress is due once per configured two-minute trigger. Before any success, the bootstrap anchor is `ops_sweep_state.monitoring_started_at`; a started run that publishes no owned progress is non-healthy. Mere invocation or lease acquisition is not progress.
- **Odds:** when D1 scheduling says no provider work is due, that successful due calculation is healthy scheduling evidence. Once a provider poll is due, its frozen due time is the obligation; only a validated successful provider result satisfies it. Timeout/failure backoff retains the original unmet anchor.
- **Backup:** each ready pool is due by `last_successful_r2_store_at + ceil(ready_pool_count / 100) * two minutes`. A never-successful pool uses `monitoring_started_at` as its bootstrap success anchor. Only a completed encrypted R2 store satisfies the obligation; cursor movement and configuration presence do not.
- **Pool lifecycle/watchdog:** every reconciliation or delivery row has an obligation at its authoritative due time. A successful provider observation that legitimately schedules the next normal incomplete-result poll satisfies the old obligation and creates a new one; an error retry that merely moves `next_attempt_at` does not. Each ready pool is also due for inspection once per published bounded cursor cycle; first timeout/error is `unknown` from that due anchor. Missing/late alarm, overdue work, exhausted outbox, and settlement exceptions remain separate findings.

For a deadline-based obligation, opening mail becomes eligible exactly 30 minutes after the frozen unmet deadline. For an observation condition with no earlier business deadline, it becomes eligible 30 minutes after `first_unmet_at`. Eligibility is evaluated on each bounded sweep, so delivery is eligible at the threshold, not guaranteed at that exact instant. There is no second grace period.

V1 persists opening and recovery transitions only—never reminders or severity-escalation mail. When a healthy observation follows an opening transition that is pending or claimed, create the recipient's immutable recovery intent immediately but keep it blocked on that recipient's opening acknowledgement. Once opening is acknowledged, exactly one recovery becomes eligible. Transition ordering is strict per `(check_kind, subject_id, recipient)` across repeated failure episodes, so a later opening for that same check and subject cannot overtake the preceding recovery; another check or subject has an independent chain. Incidents that recover before any opening transition became eligible produce no mail.

Delivery claims use an atomic conditional update with a claim token and short expiry. After every awaited send the owner must re-check the claim before acknowledging it. A provider rejection, timeout, lost acknowledgement, or expired claim leaves the immutable delivery durably retryable with the same payload and stable Resend key. Retry uses exponential backoff from two minutes capped at 30 minutes and never terminally exhausts the delivery; the cumulative attempt count is evidence, not an abandonment threshold. Each invocation attempts a delivery ID at most once, round-robins independent chain keys so one failing destination cannot starve unrelated checks/subjects, starts no more than five sends total, and never has two in-flight rows for one chain. Re-sending the same opening or recovery transition is delivery retry, not a reminder, and no reset action is needed or exposed. Resend currently retains an idempotency key for 24 hours, not forever, so provider acceptance plus lost acknowledgement or D1 history loss can still duplicate mail and remains an explicit residual.

### Implementation seams

1. **Centralize scheduler execution and fence ownership.** In `src/index.ts`, replace independent scheduled branches with one `ctx.waitUntil(runScheduledOperations(...))`. Add `src/worker/operations-cron.ts` to atomically claim a 150-second D1 lease/run token, record scheduler progress, call bounded odds and backup functions with injected clock/run token/deadline, execute one bounded watchdog page, process incident transitions, drain bounded notifications, and finalize. Renew for another 150 seconds only at explicit checkpoints when fewer than 15 seconds remain and the same unexpired token still owns the lease. Every authoritative cursor, latest-observation, incident, claim acknowledgement, progress, and completion write includes `WHERE run_token = ? AND lease_expires_at > ?`; zero changed rows means stop without publishing. An expired owner that resumes after takeover may record no recovery or completion. Independent job outcomes use `Promise.allSettled`, but every publish is still fenced.
2. **Make progress measurable.** Extend `src/worker/cron.ts`, `src/odds/ingestion.ts`, and `src/worker/backup-cron.ts` only enough to return safe outcome metadata and accept abort/deadline input. 3. **Bound the complete invocation.** Use one 110-second monotonic budget and preserve its final ten seconds exclusively for fenced observation/cursor/lease finalization. Odds and backup may run independently during the first 50 seconds: each provider HTTP request is capped at four seconds and the composed odds job at 20 seconds; backup retains the 100-pool page ceiling but stops before its 50-second deadline, gives each DO/R2 operation a bounded remaining-time signal, and persists each successfully owned pool/cursor step. Watchdog then inspects at most 20 ready pools with concurrency five, a three-second timeout per DO call, and a 30-second phase limit. Incident evaluation gets ten seconds. Notification delivery starts only while at least ten seconds remain, runs at most five independent recipient chains with an eight-second per-send timeout, and stops at the 100-second finalization boundary. No phase starts work that cannot fit its remaining sub-budget. Timeout/error writes fenced `unknown`, persists partial progress, advances only the cursor owned by the current token, and cannot recover an incident.
4. **Add read-only inspection.** In `src/durable/pool-do.ts`, install fixed `GET /internal/ops/inspection` before the command boundary and authenticate it with `OPS_SERVICE_TOKEN`. Add pure queries in `src/durable/scheduling.ts` for the earliest non-complete `event_reconciliation.next_attempt_at`, active unresolved Super Bowl discovery deadline, eligible non-exhausted outbox retry, exhausted outbox count/categories, and current `state.storage.getAlarm()`. Return only deadlines/counts/categories, never wager rows, legs, selections, member data, payload JSON, or raw errors.
5. **Serialize both settlement entry points.** Route platform `alarm()` delivery and the existing authenticated `/internal/settle` service entry through one per-object in-memory single-flight promise covering settlement, outbox draining, and final re-arming. Joining callers await the same promise and receive the same failure; this adds no operator settlement trigger. Set `alarmExecutionStartedAt` before publishing that promise and clear it only after final reconciliation/failure cleanup, so one invocation cannot clear another's running signal. Inspection reports `alarmRunning` and treats null `getAlarm()` while true as in-flight rather than missing. Cloudflare guarantees only one platform `alarm()` at a time; it does not serialize an ordinary JavaScript call from `fetch()`. Commands and repair may still run while settlement awaits D1/Queue, so accounting transactions re-read authoritative SQL and every completion uses earlier-only reconciliation. Consume SQL cursors before awaited I/O.
6. **Centralize every alarm write with explicit ownership.** Add an inner `reconcileEarlierAlarm(sql, txn)` that assumes its caller owns an asynchronous `storage.transaction(async (txn) => ...)`: it recomputes the earliest authoritative deadline through `sql`, reads `txn.getAlarm()`, and calls `txn.setAlarm()` only when pending work exists and the current alarm is null/later. On SQLite-backed objects, official documentation says top-level `storage.sql` operations issued inside that callback participate in the transaction; alarm operations use the callback's transaction interface. The helper never starts a transaction, postpones an earlier alarm, or deletes an idle/stale alarm. Ordinary command dispatch owns one async transaction containing command SQL plus reconciliation. Alarm completion owns another after external work. Repair owns one transaction containing its local audit/replay SQL plus reconciliation, so a transaction failure rolls back both audit and alarm change. Do not issue raw `BEGIN`/`SAVEPOINT` SQL or nest `transaction()`/`transactionSync()`. Queue work may never replace/delay settlement work.
7. **Classify watchdog findings.** No pending work plus no alarm is healthy. Pending work with no alarm is `missing_alarm`; alarm later than earliest required is `late_alarm`; `requiredAt < sampledAt` is independently `overdue_pending`; exhausted rows are `outbox_exhausted`; request/schema/time failures are `inspection_unknown`. `alarmRunning` suppresses only missing/late classification, not overdue or exhausted work. A future alarm with no pending work is diagnostic and allowed to fire as a no-op; repair does not delete it.
8. **Add explicit repair.** `POST /ops/api/pools/:poolId/repair-scheduling` accepts only `{operationId, reason}` after the operator boundary. It inserts `ops_repair_operation(prepared)` before calling authenticated `POST /internal/ops/repair-scheduling`. The PoolDO adds a local `scheduling_repair_operation` table keyed by operation ID/fingerprint and transactionally re-reads required work/current alarm and uses the same earlier-only helper. It records/replays `scheduled_earlier|already_correct|idle`; it never invokes `alarm()`, settlement, outbox draining, or exhausted-row reset. The Worker then completes the D1 audit. Lost responses remain `unknown/prepared`; retrying the exact operation obtains the PoolDO replay and completes D1. Different input for the same ID fails.
9. **Add ops UI and safe health.** `/ops` shows sweep freshness, configuration readiness, current incidents, observations, notification delivery, and per-pool inspection. The repair button requires a reason confirmation and retains its operation ID across repeated clicks/unknown responses via the existing `FrozenAdminCommand` pattern. Extend `health.ts` with scheduler semantics and preserve coarse public output.

PoolDO construction currently creates/migrates tables. Calling inspection on a never-before-used object therefore has bootstrap storage effects even though the endpoint itself issues no writes. Production sweep input must come only from ready `pool_registry` rows. Tests must separately demonstrate (a) an initialized object's authoritative rows/alarm are unchanged by inspection and (b) a fresh object may create empty schema during constructor bootstrap but inspection executes no command, alarm, settlement, outbox, or business write. ## Stage 2 — settlement exception isolation and controlled retry

### Authoritative schema and state

Add these tables through `poolSchema` plus idempotent checks in `migrateAdditivePoolStorage()`:

- `settlement_accounting_pass`: immutable pass ID, canonical provider-observation JSON/hash, `incomplete|complete`, started/completed timestamps, and lifecycle context. `settlement_accounting_pass_candidate` freezes the deterministic wager/evidence-key list and records `pending|applied|exception|disposed|stranded`, with terminal reason/time for `stranded`. At most one pass is incomplete. This durable barrier is independent of active season and is honored by every automatic-closure caller; retained stranded candidates remain unresolved evidence after pass completion without globally blocking later seasons.
- `settlement_exception`: primary key `(wager_id, evidence_key)`, season ID, safe typed category, retained canonical evidence JSON, `open|resolved|superseded`, first/last observed, separate observation and accounting-attempt counts, current retry operation, successor evidence, successful effect link, and resolution/supersession actor/reason/time. The evidence key is derived from ordered `(eventId, league, correctionVersion)` identities, never from poll/run ID. A partial unique index permits only one `open` row per wager while preserving all historical rows.
- `wager_evidence_disposition`: primary key `(wager_id, evidence_key)` with `accounted|commissioner_superseded`, immutable effect/command link and timestamp. Candidate selection checks every disposition, not just open exceptions, so already-applied or authorized-disposed provider evidence cannot replay.
- `settlement_exception_retry`: stable operation ID, wager/evidence key, actor, reason, request fingerprint, `failed|resolved|stale`, safe category, and timestamp. Reuse with changed input is a conflict.

Only explicitly typed deterministic accounting/domain failures are isolatable: negative account, negative float, an unsupported retained wager ruleset, or a validated corrupt per-wager accounting invariant. Network/D1/Queue/storage errors, transaction failures, parser bugs outside the per-wager evidence boundary, and unknown exceptions must propagate so alarm retry/monitoring sees an infrastructure failure. Narrow the existing broad catches in `src/durable/alarm.ts`: only result-source request/validation failures may update provider retry state; snapshot parsing, storage, transaction, and accounting failures escape unchanged and create no business exception.

### Transaction ownership and rollback design

Refactor `src/durable/settlement.ts` into pure candidate/evidence selection plus synchronous one-wager application, while retaining existing grading helpers and result identities. The implementation uses only Cloudflare Storage API transaction primitives: `storage.transactionSync()` for SQL-only rollback scopes and `storage.transaction()` when alarm APIs are included. Official SQLite storage documentation explicitly rejects transaction-control SQL such as `BEGIN` and `SAVEPOINT`. The pinned `@cloudflare/workers-types@5.20260822.1` exposes synchronous `transactionSync(callback)` but asynchronous `getAlarm()`/`setAlarm()`, so alarm changes never occur inside `transactionSync()`.

1. Before fetching newer provider data, resume the oldest incomplete accounting pass. For a new observation, one short `transactionSync()` stores terminal snapshots, creates the incomplete pass, and freezes every affected wager/evidence candidate in deterministic wager order. Lifecycle completion is retained in the pass but not published yet. From that commit onward, all automatic closure paths see the barrier.
2. For each pending candidate, call an outer transaction-owning `transactionSync()` wrapper; the inner application function accepts only `SqlStorage` and never opens a transaction. It re-reads the wager, season, legs, current settlement, accounts, retained snapshots, exception/disposition state, and pass row. A missing or invalid authoritative season is an infrastructure/invariant failure and propagates. An exact disposed evidence key marks the candidate disposed. An exact open exception increments only its observation count and marks the candidate exception; it is retried only by the explicit command below.
3. If that authoritative season is already `closed`, the candidate transaction records terminal `stranded` with reason `season_closed_before_application` and timestamp, then stops without changing account balances, season float/notional/state, wager/leg/settlement rows, evidence dispositions, command version, or outbox. The frozen pass/candidate evidence remains visible as an unresolved all-season finding; closure is neither successful accounting nor commissioner supersession. This branch does not add a post-close remedy or restrict `CloseSeason`.
4. Otherwise, a successful candidate transaction performs reversal plus replacement atomically, rejects negative account/float, updates observed leg versions, appends season provider evidence, records an `accounted` disposition linked to the settlement effect, bumps one monotonic pool/season command version, enqueues matching projection output, and marks the candidate applied. It also resolves every applicable older open intent for that wager with a link to this successful effect. Merely observing newer evidence never resolves an exception.
5. If a typed deterministic exception escapes, the candidate transaction rolls back completely. A second `transactionSync()` atomically upserts the new evidence row, increments its accounting-attempt count, makes it the one current open intent, links/supersedes an older open intent as `newer_failed_evidence` when necessary, and marks the pass candidate exception. If this evidence/audit transaction fails, propagate. Unexpected errors stop and propagate without a business exception; already committed candidates remain idempotent.
6. A final `transactionSync()` verifies that no pass candidate remains pending, applies only lifecycle transitions still valid for authoritative season state, marks the pass complete, and evaluates eligible active-season closure together. It never emits closure/accounting output for an already manually closed season. `stranded` is terminal for pass progress, so finalization releases the global incomplete-pass barrier while its unresolved finding remains visible. Every automatic closure entry—including `applyAdministrativeCorrection()`—first checks that no incomplete pass exists and that the candidate season has no open settlement exception. Explicit `CloseSeason` remains outside this barrier. Interruption at any point leaves the marker durable, blocks all automatic closure, and resumes the exact pass before a newer one is created.
7. Preserve current early multi-leg loss behavior: only an automatic partial loss may be reversed/reopened by later incomplete provider evidence, and that reversal/reopen remains inside the one-wager transaction. Manual corrections remain authoritative until complete evidence. Routine final/15-minute/24-hour reconciliation can complete only in the pass-finalization transaction; durable exception and stranded-candidate evidence, not the routine lifecycle, retains unresolved intent.

Before relying on this arrangement, add a pinned `@cloudflare/vitest-pool-workers` proof (and register it in the explicit Workers test list) demonstrating real runtime behavior rather than mocked transactions: a thrown SQL-only candidate scope rolls back all candidate writes while the later failed-attempt audit commits; failed async repair and successful-retry transactions roll back both SQL and `setAlarm()`; successful repair and retry commit SQL plus the earlier alarm; no path nests `transaction()` or `transactionSync()`. The installed `@cloudflare/workers-types@5.20260822.1` contract exposes asynchronous transaction alarm methods, but types alone do not prove mixed SQL/alarm commit/rollback behavior. If the pinned runtime contradicts the documented primitive contract, stop implementation and revise the design rather than substituting a mock.

### Inspect, resolve, and retry

- Extend the commissioner corrections view through a new PoolDO read command that returns only exception and stranded-candidate details the authorized commissioner needs: wager ID, retained result evidence, category/state, and timestamps. Members and `/ops` receive only safe counts/categories; hidden pending selections remain protected by the existing wager privacy boundary. Extend Stage 1 inspection at this point to report earliest/open exception age plus retained stranded-candidate age/counts across all seasons, and open the corresponding D1 incident immediately; queue its opening email at exactly 30 minutes unresolved, with healthy recovery only after successful accounting or authorized supersession. Manual closure and pass finalization are not healthy recovery for stranded evidence.
- Add `RetrySettlementException` to `src/durable/pool-commands.ts`, HTTP contracts/routes, and the corrections UI. The route requires same-origin CSRF, recent auth, reason, and stable operation ID. PoolDO rechecks active commissioner authority.
- Before retry, compare the requested evidence key with the one current open exception, every disposition, and the newest retained snapshots for all affected events. Any newer result makes the request `stale`; it must never replay older evidence. The commissioner must inspect the new evidence or use the existing authorized void/regrade action.
- Give `RetrySettlementException` explicit transaction ownership instead of sending it through `PoolDO.fetch()`'s ordinary outer command transaction. Successful retry owns one outer `storage.transaction(async (txn) => ...)` containing the synchronous accounting helper plus settlement/ledger/disposition, exception resolution, retry audit, processed-command replay response, command version/outbox, barrier-aware closure evaluation, and `await reconcileEarlierAlarm(storage.sql, txn)`. The helper operates on `SqlStorage` and never opens `transactionSync()`, so no transaction is nested. This is required because `enqueueOutbox()` only inserts SQL and an otherwise idle object may have no alarm. On a typed deterministic accounting failure, throw to roll back the entire async success scope, then append the failed retry audit/update and replayable typed unresolved response in a separate `transactionSync()`. Unexpected storage, transaction, or alarm failures create neither retry response nor business exception and propagate; an alarm scheduling failure must roll back all success writes.
- A successful existing commissioner void/regrade first computes and records `commissioner_superseded` dispositions for the currently retained provider evidence and marks all open exceptions for that wager superseded in the same transaction, with actor/reason/command ID; only then may its barrier-aware closure evaluation run. Thus an unchanged provider poll cannot overwrite the remedy, while genuinely newer evidence remains eligible. Failed correction changes none of these rows. Merely seeing new provider evidence or closing a season does not mark an exception fixed.
- Missing/late results remain pending and monitored; operators wait for provider truth. Commissioner regrade requires actual public corrected event evidence, and void remains an explicit administrative refund. Never invent a score/result.

Existing explicit `CloseSeason` semantics are intentionally preserved in v1: only automatic closure is blocked. The accepted bounded residual is permanent, not a recovery path: a commissioner can manually close a season with an open exception or an interrupted pass. Existing current retry/void/regrade commands then reject the closed season, and locked shares or stale accounting can be stranded. On resume, every still-pending candidate for that closed season takes the non-accounting `stranded` disposition above, allowing the pass to complete without mutating closed-season accounting. Exception and stranded-candidate inspection/counts query all seasons independently of `active_season_id` and remain visible after later season creation; the corrections UI presents retained evidence separately from its active-season action list. Closure/pass completion never resolves that incident or reopens the season. The documented workaround is preventive inspection/resolution before manual close and a closed-season annotation afterward; annotation is dispute evidence, not accounting repair. Any post-close repair or preventive manual-close restriction requires a separate user policy/design decision and is not silently added here.

### Stage 2 focused acceptance tests

- Pinned-runtime transaction proofs cover SQL rollback plus separately committed failed audit, and mixed SQL/alarm repair and successful-retry rollback/commit without nested transactions or mocked transaction semantics. From completed reconciliation with an empty outbox and no alarm, successful retry atomically creates output plus an earlier wakeup; injected alarm failure rolls the success back, while typed accounting failure commits only its separate failed-attempt audit.
- One corrupt/negative wager rolls back its reversal/replacement and records one exception while an unrelated wager settles exactly once.
- Interrupt after snapshot/pass creation, between candidate commits, and before finalization. Every automatic-closure caller observes the incomplete-pass barrier, exact candidates resume, and closure occurs only in successful finalization. Also interrupt before a candidate commits, manually close that season, open another season, and resume: the old candidate becomes `stranded` with frozen unresolved evidence, no closed-season accounting/settlement/disposition/output changes occur, pass finalization releases the global barrier, and later-season work proceeds without false recovery.
- Two polls with identical evidence increment observation separately from accounting attempts. Cover E1 failure → E2 success (E1 discharged to the successful effect), E1 failure → E2 failure (E1 linked/superseded, E2 uniquely open), and stale/failed retry replay.
- An unexpected infrastructure/storage/parser/accounting exception propagates and creates no business exception or provider-backoff row; an earlier committed wager safely replays without duplicate ledger/settlement/outbox rows.
- A failed explicit retry records its durable failed audit without partial accounting; replay returns the same result. A successful retry produces exactly one reversal/replacement, disposition, and resolution atomically, and rejects negative balances.
- Successful commissioner void/regrade supersedes current evidence/exception atomically before closure; failed correction does not. Unchanged provider polls after supersession are disposed, while newer versions remain eligible. Non-commissioner, stale session, wrong origin, and operation-ID conflict fail.
- Open exceptions and incomplete passes block `float_exhausted` and `super_bowl_final` automatic closure. Their finding is immediately visible, email becomes eligible at exactly 30 minutes unresolved, and unknown/season closure cannot recover it. Existing explicit close remains possible; closed-season exception/stranded evidence remains inspectable after a new season opens, does not resolve anything, and retry reports the non-reversible residual without reopening.
- Existing result-version idempotency, final/15-minute/24-hour correction, early multi-leg loss/reopen, immutable source evidence, commissioner correction, projection monotonicity, and closure tests remain green.

### Stage 2 rollout and rollback floor

1. Deploy additive PoolDO tables and read paths before enabling any stage-2 authoritative writer. Constructor migration must be idempotent and wall-clock independent.
2. Exercise focused fixture tests with injected deterministic failures. In production, observe exception counts only; do not manufacture an exception.
3. Before enabling accounting-pass, candidate, disposition, exception, or retry writers, record the deployed stage-2-compatible Worker version as the rollback floor and prohibit rollback to pre-stage-2 code. This gate is based on writer enablement, not a scan for exception rows: an incomplete pass or authoritative disposition/retry record can exist before any exception row.
4. Enable the stage-2 authoritative writers together. An empty exception table is expected and neither proves the path works nor makes a pre-stage-2 rollback eligible. Fixture-test a persisted incomplete pass with zero exception rows against rollback gating. After enablement, roll forward with a fix; do not roll PoolDO/D1 data back.

**Stage 2 residuals:** manual close can permanently strand an exception, a frozen pending candidate, or locked shares as described above; the resume disposition prevents a global barrier but is not accounting recovery, and there is no supported in-app post-close remedy. Provider corrections arriving after closure remain evidence requiring separate policy; they never reopen or overwrite a closed season. Per-wager commits mean an unexpected failure can leave a prefix of candidates settled before exact pass resume, but immutable dispositions make replay safe and the durable incomplete-pass barrier blocks every automatic closure path until pending candidates are terminal. Exception/stranded details remain in one PoolDO and are unavailable if that object itself is unavailable.

## Stage 3 — deployment-blocking fixture smoke, read-only postdeploy smoke, and operator canary

### Deterministic critical-path gate

Create a small Vitest project/script, for example `npm run test:critical`, using the existing Worker/PoolDO fixtures and injected clocks/providers/failures. It must run in the blocking `ci` job and be a prerequisite of `deploy`; the broad Playwright suite remains separate. Include these source-named scenarios:

- auth session, pool membership, ops allowlist, recent-auth, and CSRF denial;
- quote/place plus exact placement replay creates one wager and one locked ledger effect;
- settle plus result replay creates one settlement effect;
- deterministic exception isolation and authorized retry;
- read-only inspection and idempotent earlier-only scheduling repair, including shared-alarm race fixtures.

Do not use sleeps, network providers, browser automation, or live bindings. A failure blocks deployment. Keep the suite narrow enough to diagnose; broad presentation coverage stays in existing tests.

### Read-only postdeploy smoke and rollback metadata

Add `scripts/postdeploy-readonly-smoke.mjs` and CI wiring after deployment. It may call only public safe health endpoints that internally prove app execution, D1 query, one registered real PoolDO inspection, scheduler progress, and deployed version metadata. It must not place/settle/repair, invoke provider ingestion, drain outbox, or select an arbitrary pool. The representative pool ID is server-configured and responses remain coarse.

Use Cloudflare's version metadata binding (after verifying it in pinned Wrangler `4.125.0` types/config) or the authenticated versions API to compare the deployed version with the intended build. Capture the previous compatible version before migration/deploy and record it as the rollback candidate. Retry background freshness only until the documented expected deadline; unknown/stale is not pass. Code rollback is allowed only when binding/DO migration constraints and the stage-2 rollback floor permit it. D1/PoolDO schema is never rolled back.

### Operator-triggered canary identity and state machine

Add immutable server configuration for exactly one `CANARY_USER_ID`, `CANARY_POOL_ID`, and `CANARY_SEASON_ID`. The trigger request contains no actor, pool, season, stake, event, or selection. An allowlisted recently authenticated operator supplies only `{runId, reason}`. The trusted Worker acts as that bounded canary user; it stores no canary password/session and exposes no generic impersonation seam. Before any wager attempt it proves the configured user is an active member of the configured PoolDO and that the configured season is the current active season. Suspension and every ordinary betting/accounting constraint still apply.

Refactor quote/place handling into a service shared by public routes and the canary runner so the canary uses the same D1 offer canonicalization, betting window, freshness, quote storage, live-equivalent offer revalidation, risk/funds/exposure, and PoolDO placement path. Do not create a privileged placement command.

Add additive D1 tables `ops_canary_run` and `ops_canary_attempt`. The run stores run ID, operator/reason, immutable target/config fingerprint, fixed wager identity/minimum stake, state `pending|passed|failed|not_exercised`, safe reason and timestamps. Each of at most two attempt rows stores its own quote key, placement command ID, complete frozen public quote request/fingerprint (including selected offer identity/version and all semantic terms), complete quoted placement command, conditional owner/version, phase, typed service outcome, and timestamps. Historical attempts are never overwritten.

The shared quote/place service returns a tagged internal result—not an interpretation of HTTP status—distinguishing `pre_dispatch_rejected`, `quote_uncertain`, `placement_may_have_dispatched`, `placement_committed`, and semantic mismatch. Public and canary callers use the same D1 canonicalization, live offer refresh, PoolDO commands, and error mapping. The canary adds no privileged placement path.

1. Claim/replay the run ID. Persist target fingerprint, fixed run wager ID, minimum configured stake, and `pending` before selecting or dispatching anything. Conditional run/attempt versions ensure concurrent recovery clicks cannot choose different terms.
2. Recover any existing attempt before evaluating current new-run eligibility. For a never-started run only, prove configured membership/season/funds readiness and select the first deterministic eligible pregame straight offer ordered by kickoff/event/market/offer identity, with the fixed minimum margin/side/stake. No betting window or eligible game is `not_exercised`; closed season or insufficient funds is `not_exercised/maintenance_required` only if no quote or placement may have been dispatched.
3. In one conditional D1 write, freeze the complete public quote request and its exact `quoteRequestFingerprint`, quote key, offer identity/version, wager ID, and phase `quote_ready` before quote dispatch. Mark `quote_may_have_dispatched` before the call. A lost response or restart reuses the exact frozen request/key; it never reselects from changed D1 offers. If the immutable quote exists, `ReplayWagerQuote` returns it despite later offer changes.
4. After a quote response, conditionally persist the complete immutable placement command and command ID before any placement call. Mark `placement_may_have_dispatched` before crossing the dispatch boundary. Only the owner of that transition may dispatch; stale owners that resume fail the conditional check. Exact repeated clicks/restarts retain the same request.
5. Recover a potentially dispatched placement by exact `ProbePlacementReplay`, exact command resubmission where the frozen public-equivalent service permits it, and a new narrowly authorized configured-target PoolDO verification read. That read returns only the expected wager's immutable terms/status and causation-specific `wager_lock` ledger entry; it works after natural settlement and never accepts an arbitrary pool/user/wager from the browser. Exact wager plus exactly one matching original lock proves commit; mismatch is `failed`.
6. A replay-cache miss is never proof of non-commit: ordinary reads currently prune `processed_command` after 30 days, while wager and ledger rows remain. While quote dispatch remains uncertain, or once placement may actually have crossed the PoolDO dispatch boundary, changed funds/season/board eligibility, a replay miss, or an unacknowledged late rejection cannot retroactively produce `not_exercised` or authorize another wager. If durable positive evidence cannot resolve a potentially dispatched placement, preserve `pending/uncertain`; never infer absence from the cache.
7. A second quote is allowed at most once, uses a new persisted quote key/placement command ID while retaining the same run wager ID and first-attempt evidence, and is created only after the current owner durably records the shared service's authoritative `pre_dispatch_rejected` outcome proving the PoolDO placement boundary was never crossed, and exact quote/placement probes show no accepted effect. Lost acknowledgement of that outcome remains uncertain. Quote uncertainty or any actual/potential PoolDO placement dispatch permanently forbids re-quote/replacement for that run.
8. Pass only after the configured-target read proves one exact wager and one causation-specific original lock effect. Retain the wager; natural settlement may release current locked balance but does not erase that proof. No fake result, forced settlement, deletion, replacement wager, or unlimited replenishment is allowed.

The `/ops` canary UI shows current target readiness without IDs, previous states, and exact pending-recovery action. It disables duplicate in-flight clicks but retains the run ID after network failure. V1 is never invoked by CI. Setup requires an operator to create and fund the dedicated account/pool/season through normal authorized flows, configure exact IDs server-side, keep the season open and member active, document share availability, and periodically replace the season through normal lifecycle actions. A missing eligible game is normal `not_exercised` evidence.

## Cloudflare facts used by this design

Official documentation was retrieved successfully during the design reconciliation (no account-authenticated or production requests were made):

- [Durable Objects Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/): one alarm per object; `setAlarm()` replaces it; platform `alarm()` is single-instance and at-least-once; and `getAlarm()` returns null during a running handler unless it has since been set. This guarantee does not serialize the repository's ordinary `/internal/settle` fetch call, hence the application single-flight boundary.
- [Durable Objects SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/): transaction-control SQL including `SAVEPOINT` is unsupported; use asynchronous `transaction()` or synchronous `transactionSync()`. The page says SQLite SQL issued through top-level storage inside `transaction()` participates in that transaction. The installed Workers types expose `transaction(closure: (txn) => Promise<T>)` and asynchronous `txn.getAlarm()`/`txn.setAlarm()` methods, so successful retry can use top-level synchronous SQL and the callback transaction's awaited alarm interface in one outer async transaction without nesting. Mixed SQL/alarm atomicity still requires the pinned-runtime proof above. The same page documents per-object PITR bookmarks, approximately 30-day history, whole-object in-place recovery on the next session, and no local-development PITR.
- [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/): production-backend prerequisite, destructive in-place restore, no current clone/fork, and plan-dependent 7-day/30-day limits.
- [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/): configured UTC schedule and propagation behavior; application progress still needs its own durable heartbeat.
- [Workers scheduled handlers](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/): scheduled handlers can run for up to 15 minutes, but this design deliberately budgets 110 seconds to fit the configured two-minute cadence and reserves finalization time.
- [Workers rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/): code rollback does not restore connected data and can be blocked by changed bindings/DO migrations.
- [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys): keys are retained for 24 hours and the same request/key is safe to retry only within that provider window.

The official Cloudflare `cloudflare`, `workers-best-practices`, `durable-objects`, `cloudflare-email-service`, and `wrangler` skills were also consulted. They reinforce retrieval over memory, one-alarm replacement semantics, bounded/awaited Worker work, additive DO migration care, pinned tool/type verification, and the rule that rollback does not recover resource data.
